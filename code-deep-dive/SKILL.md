# code-deep-dive

## 触发条件

命中任一条即触发，无需用户说出 skill 名称：

- 通读或讲清一个项目、一个包、一个模块。
- 说明某段代码怎么跑，数据从哪来到哪去。
- 找易错点、风险点、隐藏的坑。
- 评估优化空间，或问"这里要不要重构"。
- 产出代码说明文档、架构文档、数据流文档、代码评审材料。

只问单个函数怎么写、或只做一次代码搜索时，不触发。

## 工具分工

- **事实源**：符号签名、调用关系、依赖、数据流以代码分析类 MCP 工具的返回为准，读原文用于核对与补充上下文。这些工具由宿主动态发现，开工前逐个在会话里探测，DSH 上名字形如 `mcp__<serverName>__<tool>`；工具名、参数、已知限制与选型表见 `references/mcp-selection.md`。会话里没有这类工具、而用户想接上时，跑 `scripts/setup-mcp.ps1`（Windows）或 `scripts/setup-mcp.sh`（macOS/Linux）：它建 venv、装 server、握手自检并打印要粘贴的配置——**配置由它打印，不要手搓路径**。
- **宿主工具**：读、搜、写文件用宿主的 read / grep / glob / write。
- **并行派发**：用宿主的子代理工具（DSH 上是 `subagent`，多阶段批量用 `workflow`；宿主没有这类工具就串行做）。条件是模块数超过 5 个、彼此独立，且用户已确认分析范围。子任务不共享上下文，派发时把模块路径、核心符号、证据账本要求、输出文件路径、以及它能否访问 MCP 一起写进 prompt。
- **降级**：只有缺工具的那项能力降级（结构用 glob + grep + 读原文；调用关系用 grep 搜符号名；数据流逐段读源码跟踪赋值与传参），其余照常走 MCP，并在交付文档开头声明本次哪些能力降级、结论处于哪一档证据。

## 全局规则

1. **事实来自 MCP**。签名、调用边、依赖、数据流以工具返回为准；读原文用来核对，并补充注释里的业务原因、错误处理与边界条件。两者冲突时以原文为准，并把偏差记进校验记录。
2. **每条结论挂证据并标档次**。结论旁写出来源工具与参数（如 `get_symbol_dependencies(order_service.create)`）；有 MCP 证据标"已验证"，只有源码依据标"推测"，无依据标"未验证"，后两档不升格写成第一档。
3. **引用三件套**。任何代码引用给 `文件路径:起-止行号`，行号以实际读到的原文为准，引用前先读过该文件。
4. **消化后转述**。MCP 原始 JSON 只进内部推理，交付文档里出现的是被解释过的结构、关系与结论。
5. **每条建议算投入产出**。给出改动成本、回归风险、收益量级，并据此判定"建议改"或"不建议改"；判定不建议改的，写进"不建议改"并给具体技术理由（瓶颈不在这一层、引入的复杂度超过收益、会破坏既有契约、缺少回归测试网、与团队约定冲突）。
6. **图与文对齐**。图上每个节点对应一个已确认的符号或一次外部边界，每条实线对应一次调用或一次数据传递；虚线只走"可能出错"的分支，且每条在易错点表里有对应行。
7. **易错点可定位**。每条落到具体字段、具体条件或具体异常分支；"注意异常处理"这类写法不算完成。
8. **先取答案再读原文**。每个符号先要签名，再要依赖，再决定读哪一段源码；整文件通读会烧掉注意力预算。
9. **文档面向人**。标题分层、表格承载对比、代码块只放被剖析的片段、结构用 Mermaid 表达；长文件给行号区间和阅读建议。中文术语首次出现后括注英文原名，全文复用同一叫法。
10. **MCP 只是事实源**。分析框架、业务判断、建议取舍由你完成；能力缺工具时写 `<MCP工具名>` 并说明要它做什么，工具名、符号名、行号都以实际返回为准。

## 前置检查

只问缺失的关键信息，用户已说的不重复问；信息足够时直接开工。

需要的是：目标项目路径、分析范围或模块清单、文档受众（新人上手 / 重构决策 / 评审 / 交接）、输出目录与文件名约定、需要重点关注的业务规则或已知故障。逐项核对，缺哪项问哪项。

**输出目录先确认可写**：DSH 只允许写会话工作区内的路径。项目在工作区外时，把文档写到工作区内并在交付时说明位置；确实要写进项目目录时，先请用户把该项目设为工作区，或授权更宽的写权限。

分析开始前读 `references/mcp-selection.md`，核对可用工具与其已知限制（例如按简单名匹配会误报的依赖边）。

## 阶段一：项目侦察

目标：产出一张带优先级的模块清单，后续工作按它推进。

1. 全局索引：调当前会话可用的索引工具（见 `references/mcp-selection.md` 的选型表），确认图是否过期；无索引工具时跳过，走降级路径。
2. 读结构统计与分层：调选型表里对应的结构工具，拿到模块清单、文件清单与依赖分层；无结构工具时走降级路径。
3. 找真实入口：调选型表里对应的检索与结构工具，定位路由、任务消费、CLI 命令等真实入口。
4. 按目录、包或领域边界划模块。
5. 标承重等级：`核心链路`（入口到落库/出网的主干）、`公共设施`（被多处引用的日志、配置、鉴权）、`边缘`（只被调用、不含业务判断）。
6. 定位核心符号：调选型表里对应的检索工具找候选，再用符号签名工具确认签名。
7. 某个模块的核心符号超过 15 个时，写明该模块的抽样规则与排除范围。

**完成标准**：模块清单表列出每个模块的路径、职责一句话、承重等级、核心符号数、优先级，每行附一条侦察期证据；抽样与排除范围已写明。

## 阶段二：逐模块分析

按优先级一次做一个模块。**模块数超过 5 个时，先把清单和优先级摆给用户确认，只做 P0/P1 模块，其余列入待办**；确认后的模块彼此独立、且宿主有子代理工具时，按"工具分工"并行派发，否则串行。

每个模块四轮：

1. **拿答案**：按 `references/mcp-selection.md` 的选型表，依次调对应工具取：符号契约 → 直接调用关系 → 跨模块依赖 → 数据流（`direction: forward`、`max_depth: 5` 起步）→ 分支与不变量 → 副作用边界。某能力无对应工具时走降级路径。
2. **读原文**：读关键符号所在文件的对应行区间，核对签名与调用点，补充注释里的业务原因、错误处理、边界条件。
3. **判投入产出**：对每处可疑代码评估改动成本、回归风险、收益量级，得出"建议改"或"不建议改"。
4. **成文**：按 `references/module-template.md` 写四章，存到输出目录。

**完成标准**：四章齐全；每条引用对应一次工具调用或一次已读源码；没有未标注的 MCP 原始输出；第二章提出的每个建议，在第四章汇总表里有对应行。

## 阶段三：汇总与校验

按 `references/output-checklist.md` 逐项过，全部通过才交付：

1. **事实核对**：抽查行号，剔除按简单名匹配造成的误报，把结论归入已验证 / 推测 / 未验证三档。
2. **图校验**：Mermaid 节点与边对得上源码，写法要求见 `references/module-template.md`。
3. **七项检查**：缺项回阶段二补齐。
4. **工具账本回填**：此时按章节回查每条结论的支撑调用，支撑不上的降档或补调用。
5. **索引与挂起项**：写总览文档，把所有"未验证"结论和未做模块列成待办交给用户。

**完成标准**：七项全部勾选；索引里每条建议能跳到来源模块文档；挂起项写明缺什么证据、补哪次调用能补齐。
